Claude Mods, drawn as machinery

A mod is a TypeScript or JavaScript module that Claude Code loads into its own event chain. It can stop, rewrite or watch almost everything the engine does, from the prompt you type to the rows written to the transcript, and it can draw its own interface. These figures show where each piece sits and what lasts how long. New to all of this? Start with Claude Mods 101.

FIGURE 1

Anatomy: three files, one door

A mod is a plugin folder whose hooks module exports register(on, options). The module runs in an environment of its own with no Node and no DOM, so everything it touches outside itself goes through $. That boundary is for isolation of code, not for safety: $ can read and write files, run processes and fetch URLs with Claude Code's own rights.

FIGURE 2

The chain: every event is an onion

When the engine raises an event, the hooks registered for it nest in tier order. Each hook gets the event e and a next. Calling next(e) runs everything beneath and resolves to the result, which the hook can return, change, or ignore. Earlier tiers wrap later ones, so an organization's managed plugins see everything first and have the last word.

Budget

10,000 ms of a hook's own time per dispatch. Time spent waiting on next or on $ calls doesn't count, except $.clock sleeps. session.end shares one short wall-clock bound across the whole chain so exit stays fast.

Pinned fields

Some fields can't be rewritten: a tool call's identity, a spawn's provider, an appended row's role and type. A rewrite of a pinned field fails the hook, which is then skipped.

One worker

Installed mods share one worker thread. A mod that crashes it or blocks it with a loop that never awaits is unloaded by name. After three crashes it can't trace, every mod that isn't built in is turned off for the session, including the organization's.

Streams

turn.step (a model request) and process.spawn (a child's output) stream. Hooks on them are async generators that can forward, rewrite or replace chunks.

FIGURE 3

Before, during, after: where each event fires

The 2.1.295 declarations list 46 engine events. Here they are placed on one session's timeline. The marking says what a hook there can do: stop the thing from happening, change it, or only watch.

Load

session.start is awaited before the first prompt, so a tool registered there is listed by turn one. Long-running work starts here with $.clock.every, which runs until cancelled or until the module reloads.

Before

prompt.submit can rewrite the text you see, attach hidden context, or drop the prompt. prompt.compose adds or replaces whole system-prompt sections, scoped shared (cacheable) or session.

During

turn.step can switch the model or effort for one request. session.append sees every row before it is stored, which is how a redactor keeps secrets out of the transcript file and the next request.

After

turn.complete returns a different text to show it beneath the answer without rewriting the record. session.measure pushes usage, so a mod never polls for it.

One tool call, end to end

The busiest path a mod sits on. Three exits leave the normal path early, and the result passes back up through the same hooks that saw the call go down.

FIGURE 5

What lasts how long

A mod has five places to keep something, and they end at different moments. A hot reload runs register again in a fresh environment and fires session.start again: module variables and timers are gone, while the host's values stay. /clear, /resume and /branch are the trap: they put every $.state value back to its default without firing session.start.

$.store

The plugin's own key-value store of JSON data, one file under ~/.claude/plugins/store/, shared by every session on the machine. It lasts until the mod deletes it or nothing touches it for cleanupPeriodDays. $.fs.write isn't atomic, so data several sessions change belongs here.

$.state

Named, versioned values the host holds for the session, declared in a PluginState contract. Only the owner writes; update($, atom, fn) retries on a version miss so two quick presses both land.

Transcript

Whatever session.append's chain answers is what gets stored, sent to the model and read back on --resume. A mod can also append its own rows with $.session.append, labelled with its name.

FIGURE 6

Where a mod can draw

Drawing is an event like any other. A ui.render hook gets one component instance, can return its own tree built from the surface's element table, and can pass the rest through with next(e). Hooks run everywhere Claude Code runs, but drawing shows up in two places today: the terminal (including editor terminals and JetBrains) and the Code tab of the Desktop app. The VS Code chat panel, claude -p, the Agent SDK and cloud sessions run the hooks and draw nothing, and Remote Control draws in the terminal on your machine.

Who can turn a mod off

Mods are on by default from 2.1.287. These are the switches, from the widest to the narrowest. Built-in mods ignore most of them.

SwitchWho sets itEffect
Remote switchAnthropicTurns installed mods off in every process; nothing on the machine turns them back on. The log reads hooks modules are turned off in this process.
disableAllHooksAny settings fileIn managed settings, no mod or hook from an installed plugin runs. In your own settings, what the organization manages keeps running.
allowManagedHooksOnlyManaged settingsBlocks hooks and installed mods that aren't the organization's.
allowManagedModsOnlyManaged settings, an option on sec-defaultOnly the organization's mods and built-ins load; users' settings hooks keep running.
prependPlugins, appendPluginsManaged settingsSeat the organization's mods before or after every user mod, in the listed order.
disableSideloadFlagsManaged settingsRejects --plugin-dir and --plugin-url at startup.
allowModsToOverrideDenyRulesManaged settings, an option on sec-defaultLets a user's mod approve a call a deny rule refuses. Off unless set.
plugin.register hookA policy modRefuses any module before it joins the chain, judged by its tier and the $ calls it uses.
--safe-modeYou, per runStarts with no installed plugin loaded at all, mods included.

Before installing someone else's mod, run claude plugin validate on it. It lists every event the mod hooks and every $ call it makes, so a mod that hooks session.append or calls $.http.fetch says so up front.

Samples, placed on the timeline

Four small mods written for this guide, one per phase. Each validates with claude plugin validate, type-checks against the 2.1.295 declarations, and passes its tests under claude plugin test. They live in ~/Projects/claude-mods/samples/ours/.

blast-guard is a teaching sample, not a safety control. Like any mod guard it fails open: if the hook throws or overruns its budget, the command runs. Pattern deny-lists are also easy to get around. A guard you rely on belongs in managed settings or the prepend tier, with a .catch handler.
